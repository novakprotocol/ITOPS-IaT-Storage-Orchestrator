    How this controlled document is created and edited

    The canonical repository supplies the Python engine, document contract, and reader theme. Every SOP, IOP, MOP, runbook, standard, design, plan, training package, catalog, or other controlled artifact is created as its own private repository and edited in that repository. The Pages site is the controlled reading surface; content changes occur through the repository so authorship, review, approval, and history remain attributable.

    1. Create a new private controlled-document repository with Use this template. Do not write an actual controlled document in the canonical engine/template repository.
    2. Run python -m iatdocs init or point an approved AI agent to AGENTS.md and the machine-readable contract.
    3. Set the document ID, owner, creator, repository, version, last-review date, next-review date, and effective date in data/document.json.
    4. Edit controlled Markdown under content on a branch. Use a pull request for review and approval.
    5. Record material releases in data/revisions.json, including editor, reviewer, approver, change summary, and supporting reference.
    6. Run python -m .\doc2210.cmd validate and python -m .\doc2210.cmd build --strict.
    7. After merge to main, the GHE workflow publishes the generated static site. Open browser tabs detect the newer build and display an update notice. Refreshing saves and restores the reader’s place.
    8. The metrics command refreshes GHE repository size, recent edits, contributor percentages, word activity, and root-level Work Ledger integration records.

    Engine versus derived document: the canonical repository controls reusable compilation, presentation, behavior, schemas, and policy. Each derived document repository controls its own content, permissions, creator, revisions, Git history, Pages publication, and Work Ledger mappings.

    1. What the Console Adds

    The top of this reader now includes the missing operator views: approval queue, running-now status, last runs, next runs, receipt browser, failure view, dispatcher health, and SHA evidence.

    Public-safe rule

    The browser can generate drafts and show redacted status. The private control repository is the authority for real enable/disable state, approvals, releases, and receipts.

    2. Approval Model

    An approval is not a note. It is a structured object in the private control repository. A real enablement must identify the job, requested state, approver, approval reference, approved commit SHA, and effective state.

    {
  "schema_version": "1.0",
  "approval_id": "APPROVAL-EXAMPLE-0001",
  "change_type": "job-enabled-state",
  "job_id": "example-daily-inventory",
  "requested_enabled_state": true,
  "approval_status": "draft-example",
  "requires_private_control_repo_commit": true
}

    3. Runtime State Model

    Runtime state answers what is running now, what ran last, what is scheduled next, and what failed. In the current setup execution is disabled, so the running-now table is intentionally empty.

    Runtime view Source path in private control repo Public result now

    Last runs status/last-runs.json Not run / execution disabled
    Next runs status/next-runs.json None while disabled

    4. Receipt Model

    A receipt proves what happened. Every future execution should record job id, server id, scheduled slot, actual start, finish, result, active control commit, active script hash, and output hash.
